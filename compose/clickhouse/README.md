# ClickHouse-кластер: odin + loki

Два независимых сервера ClickHouse, объединённые в кластер `sharded` из
2 шардов (без репликации данных). Данные делятся между узлами; для запросов
"по всему кластеру" используется таблица с движком `Distributed`.

На обоих узлах поднят встроенный **ClickHouse Keeper** (кворум 2 из 2) —
он нужен только для `ON CLUSTER` DDL, не для репликации данных: MergeTree
локальных таблиц остаётся не реплицированным. Это значит, что падение
любого из двух серверов останавливает `ON CLUSTER`/DDL до восстановления
соседа (нет большинства в кворуме 2 из 2), но не трогает уже созданные
таблицы — прямые `SELECT`/`INSERT`, минующие DDL-очередь, продолжают
работать на выжившем узле.

Оба узла запускаются из одного и того же compose-шаблона
(`docker-compose.yaml` + `config/`), различие — только в `.env` на каждом
сервере.

В корне репозитория для справки лежат `.env.odin` и `.env.loki` — они в
`.gitignore` и через git не доставляются (в том числе чтобы не светить IP
серверов в репозитории), так что на сервер их нужно перенести отдельно
(scp) либо просто создать `.env` руками с нужными значениями:

```dotenv
CLICKHOUSE__NODE_NAME=dwh-ch-1          # dwh-ch-1 на odin, dwh-ch-2 на loki
CLICKHOUSE__ODIN_IP=...                 # IP сервера odin
CLICKHOUSE__LOKI_IP=...                 # IP сервера loki
CLICKHOUSE__KEEPER_SERVER_ID=1          # 1 на odin, 2 на loki — должны различаться
CLICKHOUSE__USER=...                    # логин для межшардовых Distributed-запросов
CLICKHOUSE__PASSWORD=...                # пароль пользователя
```

Логин/пароль для межшардовых Distributed-запросов не зашиты в XML:
`config.d/cluster.xml` читает их через `from_env` из переменных окружения
контейнера `CLICKHOUSE_USER` / `CLICKHOUSE_PASSWORD`.

## Развёртывание

На каждом сервере (репозиторий склонирован/скопирован целиком, `.env` создан
как описано выше):

```bash
# на odin
docker compose up -d

# на loki
docker compose up -d
```

Контейнер использует `network_mode: host` — слушает порты напрямую на
интерфейсе сервера, без проброса. Из-за этого наружу открыты все порты,
которые включены в `config/config.xml` и `config/config.d/*.xml`, а не
только нужные. **На обоих серверах нужен firewall**, ограничивающий доступ
снаружи как минимум до:

- `8123` — HTTP
- `9000` — native TCP (клиенты + межшардовые запросы)
- `9181` — Keeper (клиентский порт, нужен только между odin и loki)
- `9234` — Keeper Raft (нужен только между odin и loki)

Остальные порты (mysql_port 9004, postgresql_port 9005 и т.п.) — закрыть
или явно выключить в конфиге, если не используются.

## Проверка кластера

```sql
SELECT * FROM system.clusters WHERE cluster = 'sharded';
```

Должны быть видны обе реплики (odin, loki), `shard_num` 1 и 2, `is_local` = 1
у своего узла и 0 у соседнего.

## Проверка Keeper

```sql
SELECT * FROM system.zookeeper WHERE path = '/';
```

Если Keeper не поднялся или нет кворума — запрос зависнет/упадёт по
таймауту. Быстрее проверить статус узла Keeper напрямую (4-letter command):

```bash
echo mntr | nc localhost 9181
```

В выводе `zk_server_state` должно быть `leader` на одном из узлов и
`follower` на втором (не `standalone` — это означало бы, что узел не видит
соседа и работает в одиночку).

## Пример распределённой таблицы

Keeper поднят — DDL можно накатывать один раз, `ON CLUSTER` разошлёт его на
оба узла:

```sql
CREATE TABLE events_local ON CLUSTER sharded
(
    event_date Date,
    event_id   UInt64,
    payload    String
)
ENGINE = MergeTree
ORDER BY (event_date, event_id);

CREATE TABLE events ON CLUSTER sharded
ENGINE = Distributed('sharded', currentDatabase(), 'events_local', rand());
```

`rand()` — ключ шардирования (данные при `INSERT INTO events` случайно
раскладываются по узлам; замените на осмысленный ключ, если нужна
предсказуемая маршрутизация, например `intHash64(event_id)`).

Дальше пишете и читаете через `events` — ClickHouse сам разошлёт
INSERT/SELECT по обоим узлам.

## Ограничения выбранной схемы (шардирование без репликации)

- Данные не реплицированы: если один сервер недоступен, его доля данных
  недоступна (INSERT в `Distributed` на "живой" шард пройдёт, но запись,
  попавшая на упавший узел, задержится/отвалится по таймауту, а SELECT по
  всему кластеру вернёт неполные данные).
- Keeper держит кворум 2 из 2 — это не отказоустойчивость, а просто
  удобство `ON CLUSTER`. Падение любого узла останавливает DDL и вообще
  все операции, ждущие кворума, до восстановления соседа.
- Если позже понадобится реальная отказоустойчивость данных — это
  отдельная задача: `ReplicatedMergeTree` вместо `MergeTree`, и для
  честного кворума Keeper нужен третий узел (например, лёгкая
  witness-нода без ClickHouse) либо асимметричная схема 2+1 на
  существующих серверах.
